# ADR-0008 — Wallet unlock (mobile): the locked screen reflects the attempt, and stops lying about how the wallet opens

- **Status:** Proposed. No implementation.
- **Date:** 2026-08-14
- **Driver:** a user report that unlocking with a fingerprint on a slow connection leaves the icon, the copy and the UNLOCK button on screen while the app is already logging in, so the button can be pressed again. Grilled into a decision tree, then reviewed adversarially.
- **Reviewed by:** two Codex passes (devil's advocate on v1, adversarial on v2), each finding verified against source before acceptance — see [Review notes](#review-notes). The second pass reversed decision 2.
- **Related:** nothing supersedes or is superseded. [ADR-0006](0006-liquid-connect-acceptance-gate.md) decision 4 diagnosed the `Navigator.pop` carrier that recurs here.

## Context

`WalletLocked` (`lib/screens/home/wallet_locked.dart`) is 78 lines and watches nothing. A logo, a fingerprint icon, "Touch to unlock", an UNLOCK button — and the whole screen wrapped in a `GestureDetector` firing the same action as the button. It renders identically whether the app is idle, unlocking, or has just failed to unlock.

The state it would need already exists and is already produced. `ServerLoginState` (`lib/models/connection_models.dart:5-13`) carries `logout`, `loginProcessing`, `login` and `error({String? message})`, and `SideswapWallet._login()` sets `loginProcessing` immediately before sending the request (`lib/providers/wallet.dart:1303-1306`). Nothing reads it: grepped across the repo, `ServerLoginStateLoginProcessing` is constructed once and matched nowhere.

So the change is small. What made it worth an ADR is that the two obvious readings of "handle the failure" are both wrong, and that the tidiest-looking answer for the PIN path — take the affordances away and seal the dialog behind them — was designed, reviewed, and then abandoned on evidence. Decision 2 records why, because it is the kind of thing a later reader would otherwise propose again.

### What the measurements showed

Rust citations are against `sideswap-io/sideswap_rust` at `f53ba9d`, verified in the working copy and confirmed in sync with `origin/main`.

- **Login does not wait for the server.** `try_process_login_request` calls `send_ws_connect()` fire-and-forget (`sideswap_client/src/worker.rs:2252`) and returns `Ok` regardless. The websocket loop retries forever — 1 s doubling to a 15 s cap with ±30 % jitter, each attempt capped at a 30 s connect timeout (`sideswap_common/src/ws/manual.rs:119-139`, `retry_delay.rs:54-62`) — and emits **nothing** to the UI until it connects: neither `ServerConnected` nor `ServerDisconnected`. A wallet whose registration is cached therefore logs in with no network at all, and the user lands inside the app with empty balances. There is no "connection failed" for the locked screen to react to, and no timeout would find one.
- **The wait the user actually sees is local, and where it sits matters more than what causes it.** `gdk_ses_rust::start_processing` (`worker.rs:2105`) runs synchronously on the single-threaded worker and builds two `lwk_wollet` wallets in sequence (`gdk_ses_rust.rs:783-789`), each replaying its on-disk update log file by file. Both `From::WalletLoaded` (`worker.rs:2249`, reached because `skip_wallet_sync()` is hardcoded `true` at `:3073`) and `From::Login` (`:2272`) are only produced afterwards. **This is the load-bearing fact for this ADR**: whatever the cost turns out to be, it lands wholly inside `loginProcessing`, which is why that state is the right thing to render.
  > The two replies are not interchangeable and arrive in a fixed order: `WalletLoaded` first, then `Login`. Dart answers the first by moving to `Status.registered` or `Status.ampRegister` (`lib/providers/wallet.dart:598-608`) — which unmounts this screen — and only the second clears `loginProcessing` (`:1968`). So the screen is always removed *while still in* `loginProcessing`, and never observes `ServerLoginStateLogin`. That is the intended shape, not a gap: the screen renders one state and is taken away by the router. It does mean the dots can flash for a frame or not paint at all when the wallet opens quickly, which is the accepted cost of not inventing a second state to smooth it.
  > The likely cause is a suspect, not a finding: the update log is never compacted, because `merge_updates` returns early without a threshold (`lwk_wollet/src/update.rs:92-96` in `sideswap-io/lwk` rev `4a0a993`, which `[patch.crates-io]` substitutes for the published crate — `sideswap_rust/Cargo.toml:98-101`) and `merge_threshold` is set nowhere. It grows with state-changing syncs rather than with logins, since consecutive tip-only updates overwrite the previous file (`update.rs:142-173`, `:225-232`). **Nobody has counted the files or timed the load on a device, and nobody is being asked to.** Chasing it was considered and dropped as too deep for the problem at hand; this paragraph is the record, so the next person to wonder why unlocking is slow starts here rather than from nothing. To measure it: count the files under `<network>/enc_cache/<descriptor-hash>/` for each of the two accounts, then bracket a cold start between the `process login request...` log line (`worker.rs:2010`) and the second `lwk wallet loading succeed` (`gdk_ses_rust.rs:793`). Nothing in this ADR depends on the answer.
- **Login failures carry a message in practice, but the type does not guarantee one.** There is one construction site for `ErrorMsg` (`worker.rs:2270`), fed by `?` out of `try_process_login_request`: a bad mnemonic, a Jade open failure, missing watch-only data, a GDK error, or — first login only — a 15 s timeout registering against Blockstream Green. The current Rust code always sets `result: Some(res)`, so `notSet` is not produced today. It is nonetheless *representable*: `result` is a proto2 `oneof` with no member required (`sideswap_client/proto/sideswap.proto:472-475`), the generated Dart maps an unset oneof to `notSet`, and `_handleLogin` turns that into `ServerLoginStateError()` with a **null** message (`lib/providers/wallet.dart:2018`) — which `app_main.dart:178` does not match, so today it produces silence. An `errorMsg` selected with an empty string is representable too, and yields a non-null but blank message. The screen therefore treats null and empty identically and never renders a bare error with no text.
- **The PIN dialog resolves by whatever route is on top, not by its own.** `PinProtection` signals success with an unscoped `Navigator.of(context).pop(true)` (`lib/screens/pin/pin_protection.dart:83`), while `onPinBlockade` awaits one particular `showDialog` future (`lib/app_main.dart:156-164`). If any other route sits above the PIN dialog when the PIN is accepted, the pop lands on that route and the PIN dialog stays. Re-entering the PIN does not recover it: `pinUnlockStateProvider` is already `success`, so the `useAsyncEffect` keyed on `[pinUnlockState]` does not fire again. [ADR-0006](0006-liquid-connect-acceptance-gate.md) decision 4 identifies this same carrier as the root of three separate defects, but routes Liquid Connect around it rather than fixing `onPinBlockade` — so for the unlock path it is still live.
- **The "three wrong PINs" exit does not reliably land.** `settingsDeletePromptConfirm` runs `popUntil((route) => route.isFirst)` and then `setStatus(Status.noWallet)` (`lib/providers/wallet.dart:1531-1541`). That pop completes the pending `pinBlockadeUnlocked` with `false`, whose continuation in `unlockWallet` then writes `Status.lockedWalet` over it (`:1585`). `deleteConfig()` has meanwhile cleared `usePinProtection` (`lib/providers/config_provider.dart:292-298`), so the user lands on the locked screen in its *biometric* shape, holding a button that can no longer unlock anything. This is a pre-existing defect. It was load-bearing for the version of decision 2 that was abandoned — that version needed this exit to be clean — and is recorded here because it is still there.
- **Which means the root handler intercepts all of them.** `app_main.dart:176-189` matches `ServerLoginStateError(message: String msg)`, shows a modal, then sets `Status.noWallet` — which renders `FirstLaunchPage`, "CREATE NEW WALLET / IMPORT" (`lib/providers/route_providers.dart:152`). Leaving that handler alone and adding a failure branch to the screen would have produced dead code, because the screen is gone before the branch could run.
- **The PIN dialog can be dismissed, and `showBackButton` is a lie.** `unlockWallet` passes `showBackButton: false` (`wallet.dart:1578-1580`); `onPinBlockade` accepts the argument and never uses it (`app_main.dart:151-165`). So `PinProtection` always carries its app-bar close button (`lib/screens/pin/pin_protection.dart:33-38`) and always lets the system back gesture pop it (`:40-44`).
- **A PIN wallet is routed to this screen and told to use a fingerprint.** `unlockWallet` sets `Status.lockedWalet` whenever the PIN dialog closes without unlocking (`wallet.dart:1585`), and the screen it lands on shows `Icons.fingerprint` and "Touch to unlock" unconditionally.
- **Failing the PIN is destructive and already well-signposted.** Three wrong entries reach `PinUnlockState.failed()` and `settingsDeletePromptConfirm()` (`lib/providers/pin_protection_provider.dart:228-233`), with the dialog counting the attempts down first and warning about deletion on the last one (`:237-241`).
- **The PIN path has a network error and the biometric path does not.** PIN decryption is server-assisted, so `From_DecryptPin_ErrorCode.NETWORK_ERROR => 'Connection failed'` exists (`pin_protection_provider.dart:236`). Nothing equivalent exists for biometrics.
- **Cancelling the biometric prompt is silent by construction.** `EncryptionRepository._process` catches `PlatformException` and returns an empty buffer (`lib/common/encryption.dart:81-89`), so `decryptBiometric` yields `''`, `validateMnemonic('')` is false, and `unlockWallet` falls off the end with no `else` (`wallet.dart:1603-1605`). Nothing distinguishes a cancel from a failure.

## Decisions

### 1. The locked screen renders the unlock attempt, and only the attempt

While `serverLoginProvider` is `ServerLoginStateLoginProcessing`, the screen shows the app's pulsing-dots indicator and no affordance. Outside that state it shows what it shows today.

The spinner is **not** extended backwards over the platform biometric prompt. During that prompt the state is still `logout`, the OS sheet is in front of the app, and cancelling it produces no signal at all (see measurements) — so covering it would mean inventing a state that nothing can reliably clear.

### 2. A PIN wallet gets the same shape as a biometric one, told truthfully

The locked screen renders `loginProcessing` as the dots for a PIN wallet exactly as it does for a biometric one. Outside that state it keeps an icon, a line of copy and a working button — but ones that are **true for a PIN wallet**: not a fingerprint, and not "Touch to unlock". Pressing the button raises the unlock dialog again.

The dialog stays dismissible. `onPinBlockade`'s unused `backButton` argument (`lib/app_main.dart:151-165`) is left alone.

**This reverses an earlier version of this decision, and the reversal is the interesting part.** That version emptied the screen for a PIN wallet — logo and dots only — and sealed the dialog so nothing could be stranded behind it. It was rejected on evidence, not taste:

- **The screen it emptied is not on the happy path at all.** A PIN wallet keeps a non-empty `mnemonicEncrypted` (`_registerWallet` always writes one, `lib/providers/wallet.dart:1054-1071`; `enablePinProtection` only flips flags, `lib/providers/pin_setup_provider.dart:424-427`), so startup takes the branch at `wallet.dart:310` with the status still `Status.walletLoading` — meaning `PreLaunchPage`, which already shows these very dots, is what stands behind the first dialog. `Status.lockedWalet` is reached only *after* a dialog closed without unlocking (`:1585`).
- **The dialog has nowhere to show a login failure.** `PinProtectionStateError` is fed only by PIN-decrypt errors, and `init()` clears `pinProtectionStateProvider` on every open (`lib/providers/pin_protection_provider.dart:101`). A login error lives in `serverLoginProvider` and the dialog would never display it.
- **A sealed dialog has no timeout to escape through.** PIN decryption is a server round trip whose Rust agent sets no read timeout (`sideswap_common/src/pin.rs:47`), and pressing Enter puts the dialog into `waiting`, where keys are ignored (`pin_protection_provider.dart:197`). A hung server would hold a sealed dialog open indefinitely.
- **The safety net that was supposed to make sealing survivable is itself unsound**, in three separate ways: it collides with the second `unlockWallet()` already issued at `wallet.dart:321-325` and raises two dialogs; its guard reads `onPinBlockadeCallback`, a plain field with no reactivity, so a check made while it is null never retries; and `init()`/`deinit()` never reset `pinUnlockStateProvider`, so a reopened dialog can observe the previous `success` and close itself immediately, while its uncancelled keyboard subscription lets overlapping dialogs consume each keystroke twice.

Keeping the button makes all four moot. Every one of them ends in a dead end only when there is nothing on the screen to press; with a button, each is a recoverable annoyance rather than a wallet that needs the app killed. The cheap fix beats the correct-looking one here because the defects it would have had to outrun are in a subsystem this change does not otherwise touch.

A login failure in PIN mode is therefore rendered on the locked screen, the same way and in the same place as for a biometric wallet — which is also the only mechanism that can actually show it.

### 3. A failed unlock does not claim the wallet is gone

When `pageStatusProvider` is `Status.lockedWalet`, the root error handler shows no modal and does not navigate; the screen owns the failure and brings back the icon, the copy and the button with the message beneath them. Every other caller keeps today's modal-then-`Status.noWallet` behaviour.

**It still invalidates `serverLoginProvider`, and the screen keeps its own copy of the message.** Retaining the error state instead would be a worse bug than the one being fixed: `FirstLaunchPage` disables **all three** of CREATE NEW WALLET, IMPORT and Jade while `serverLoginState is ServerLoginStateError` (`lib/screens/onboarding/first_launch_page.dart:165`, `:199`, `:226`). A user who later reaches `Status.noWallet` — which a wallet deletion does — would find every button dead and "Connection issues detected" above them. The provider is `keepAlive`, so nothing else would clear it.

Sending a user to "CREATE NEW WALLET / IMPORT" is a claim about their wallet, and at this point the claim is false — the encrypted mnemonic is still on the device and the only thing that failed was an attempt to open it.

## Consequences

- Two files outside `WalletLocked` change: `app_main.dart` for the carve-out and the `backButton` argument, and `prelaunch_page.dart` to source its dot animation from a shared widget.
- The failure branch on the locked screen covers failures the *client reports*. It does not cover being offline, because being offline is not a login failure — see the first measurement. Making disconnection visible anywhere in the mobile app is a separate, unaddressed problem.
- **Several defects in the PIN subsystem are left in place, deliberately.** Keeping the button means none of them can strand a user, so none of them blocks this work — but they are real, they were measured here, and they are worth fixing on their own terms: the unscoped `Navigator.pop` in `lib/screens/pin/pin_protection.dart:83`; no read timeout on the PIN server round trip (`sideswap_common/src/pin.rs:47`); `pinUnlockStateProvider` surviving `init()`/`deinit()` (`lib/providers/pin_protection_provider.dart:101`); the uncancelled keyboard-stream subscription; and the deletion race at `lib/providers/wallet.dart:1531-1541` versus `:1585`.
- The screen still shows a PIN wallet content it has to get right, so the copy and the icon are now conditional where they were constant. That is a small ongoing obligation: anything added to this screen has to answer "and what does that say for a PIN wallet?"
- The dots mask a wait whose cause is untouched here and not yet measured. If that cause is the uncompacted LWK update log, unlock time keeps growing with wallet *activity* — not age — and the dots will show for longer and longer. That is a reason to measure it one day, not a reason to hold this ADR.
- **Being offline stays invisible, and it is worse than it looks.** Login never waits for the connection, so an offline unlock succeeds and drops the user inside the app. The balances they then see are not empty: they are summed from the locally cached UTXO set (`worker.rs:483-486`, `:513-519`) via a purely local `get_utxos()`, so the numbers render normally and are as old as the last successful sync, with nothing saying so. The only thing anywhere in the mobile UI that reports the connection is a `Connecting ...` line in the empty state of one order list (`lib/screens/markets/widgets/working_orders_empty.dart:34`). A wallet showing a confident, correctly formatted, arbitrarily stale balance is trusted and should not be. Deciding what to show, where, and after how long was ruled out of this work; this is the record that the question is open.

## Review notes

Findings from the review passes that **changed** the design, rather than confirming it. Each was verified against source before being accepted.

Devil's advocate, on the first version:

- The LWK update log grows with state-changing syncs, not with logins — consecutive tip-only updates overwrite the previous file (`lwk_wollet/src/update.rs:142-173`, `:225-232`) — and the dependency is our own fork, not the published crate (`sideswap_rust/Cargo.toml:98-101`). More importantly, nothing about the wait had been *measured*. The claim was demoted from a finding to a suspect, and its issue now leads with the measurement.
- `PinProtection` signals success with an unscoped `Navigator.pop` while `onPinBlockade` awaits one specific dialog future → the first prerequisite in decision 2. Without it, sealing the dialog turns a wrong-route pop into a state only an app restart escapes. ADR-0006 decision 4 diagnosed the same carrier and routed Liquid Connect around it rather than fixing it here.
- `settingsDeletePromptConfirm`'s `popUntil` completes the pending PIN future, and `unlockWallet`'s continuation then writes `Status.lockedWalet` over the `Status.noWallet` the deletion just set → the second prerequisite in decision 2, and the removal of "three wrong PINs" from the list of clean exits.
- `From_Login.result` is a proto2 `oneof` with no required member, so a null message is representable even though the current Rust never sends one → the claim was narrowed, and the screen now treats null and empty alike.
- `WalletLoaded` unmounts the screen before `Login` clears `loginProcessing`, so the screen never observes `ServerLoginStateLogin` → recorded as intended behaviour rather than left implicit, along with the accepted frame-flash on a fast login.

Adversarial, on the second version:

- A PIN wallet keeps a non-empty `mnemonicEncrypted`, so cold start takes `wallet.dart:310` with the status still `walletLoading` — `PreLaunchPage`, not `WalletLocked`, stands behind the first PIN dialog → decision 2 reversed. The screen the earlier version emptied is only reached after a dialog closed without unlocking.
- `PinProtectionStateError` carries PIN-decrypt failures only, and `init()` clears it on every open, so re-raising the dialog could never have shown a *login* failure → decision 2, and the error now renders on the screen for both credentials.
- The PIN server round trip has no read timeout (`sideswap_common/src/pin.rs:47`) and `waiting` ignores keys, so a sealed dialog had an unbounded hang with no escape → decision 2.
- The proposed safety net collided with the existing second `unlockWallet()` at `wallet.dart:321-325`, guarded on a non-reactive field, and could reopen a dialog that immediately closed on a stale `success` → decision 2. Three independent faults in the mechanism meant to make sealing survivable.
- `FirstLaunchPage` disables all three of its buttons while `serverLoginState is ServerLoginStateError` (`first_launch_page.dart:165`, `:199`, `:226`), so retaining the error state after the carve-out would have produced a first-launch screen with nothing usable on it → decision 3 now invalidates as before and the screen keeps its own copy.
- The update files live under `<network>/enc_cache/<descriptor-hash>/`, not the account directory, and an idle wallet's log does not grow at all → corrections in the LWK issue.
