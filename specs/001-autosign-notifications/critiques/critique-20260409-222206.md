## Product Lens Findings

### 3a. Problem Validation

**P1 — 🎯 Must-Address — Hardcoded 100 threshold lacks explicit product rationale**
- Finding: `FR-004` hardcodes 100 USDT per component but does not define why 100 is safe/default-optimal for initial launch cohort.
- Risk: weak rationale can produce churn (too strict) or unsafe signing comfort (too permissive).
- Suggestion: add explicit rationale + review trigger.
- Specific edit:
  - `spec.md`: under `FR-004b` add: "Initial threshold 100 is a launch guardrail chosen to minimize over-authorization risk; revisit after 30 days using autosign fall-through rate and support signals."
  - `spec.md`: add success metric `SC-006`: "Threshold review completed within 30 days post-launch with decision log (keep/increase/decrease)."

### 3b. User Value Assessment

**P2 — 💡 Recommendation — Auth-cancel drop flow is safe but weakly explainable**
- Finding: canceled/failed auth leads to drop with no notification by design.
- Risk: user may not understand why dApp action "did nothing".
- Suggestion: keep no-notification rule, but make behavior explicit in product copy/docs and QA checklist.
- Specific edit:
  - `spec.md` clarifications: add one sentence: "When auth is canceled/failed during autosign, no in-app sign notification appears; user must retry action from site."
  - `plan.md` manual verification: add case "auth cancel/fail -> no notification + no accept response path expected by current FR."

### 3c. Alternative Approaches

**P3 — 💡 Recommendation — Include v2 direction for configurable limits**
- Finding: configurable limit out-of-scope is acceptable, but no explicit v2 trigger criteria.
- Risk: iteration may stagnate on fixed limit despite evidence.
- Suggestion: define trigger threshold for promoting configurable limits.
- Specific edit:
  - `spec.md` assumptions: add "If >15% autosign-eligible intent falls through due 100 cap for 2 consecutive weeks, open v2 configurable-limit spec."

### 3d. Edge Cases & UX

**P4 — 🎯 Must-Address — Silent ignore of unknown origins is user-safe but operationally opaque**
- Finding: `FR-011` mandates no response and no notification for unknown origin.
- Risk: legitimate request can appear as unexplained no-op from user/site perspective; hard support diagnosis.
- Suggestion: preserve silent UX, add non-user-facing observability.
- Specific edit:
  - `plan.md` key notes near FR-011: add debug log + telemetry counters (`sign_request_unknown_origin_total`) with domain hash/redaction.
  - `spec.md` FR-011 append: "Silent ignore remains user-visible behavior; implementation must emit internal diagnostic signal."

### 3e. Success Measurement

**P5 — 💡 Recommendation — Missing safety/quality rollout metrics**
- Finding: current SCs cover behavior correctness but not misclassification or abort quality.
- Risk: cannot quantify whether autosign harms trust.
- Suggestion: add two post-launch quality metrics.
- Specific edit:
  - `spec.md` add:
    - `SC-007`: "0 known auto-accepts when component value > threshold in QA/prod incident review."
    - `SC-008`: "Unknown-origin ignore events observable in telemetry dashboard within 24h."

## Engineering Lens Findings

### 4a. Architecture Soundness

**E1 — 🎯 Must-Address — Async `_handleSignerRequest` can alter message sequencing semantics**
- Finding: `_recvMsg` now awaits signer handling; auth UI wait can delay subsequent message handling.
- Risk: ordering/latency side effects across unrelated message types.
- Suggestion: lock sequencing intent explicitly.
- Specific edit:
  - `plan.md` `_recvMsg` section: add explicit rule: "Signer handling is serialized by receive loop; acceptable because sign frequency low. Re-validate active session + autosign state immediately before emitting accept/reject."
  - `plan.md` risks table: add mitigation for prolonged auth wait and backpressure.

### 4b. Failure Mode Analysis

**E2 — 🎯 Must-Address — FR-011 timing race may drop borderline-valid requests**
- Finding: if session removed just before request arrival, FR-011 silently drops.
- Risk: user-perceived nondeterminism.
- Suggestion: document intentional policy and tighten deterministic check points.
- Specific edit:
  - `spec.md` edge cases: add "If session is no longer active at processing start, request is intentionally ignored as stale/unauthorized."
  - `plan.md`: add "session existence checked at handler entry and rechecked before final accept send after any await."

### 4c. Security & Privacy Review

**E3 — 💡 Recommendation — Domain matching normalization unresolved**
- Finding: plan says exact match preferred unless helper exists.
- Risk: inconsistent canonicalization (case, scheme, trailing dots) can reject valid requests or admit unexpected ones.
- Suggestion: freeze canonical matching rule in spec.
- Specific edit:
  - `spec.md` assumptions: define canonical domain normalization policy (or explicit exact-byte match).
  - `plan.md` implementation notes: reference single matcher function.

### 4d. Performance & Scalability

**E4 — 🎯 Must-Address — "Current price at request time" lacks freshness bound**
- Finding: `pricesUsd` can be stale; spec only says current source.
- Risk: stale quote could incorrectly keep component under threshold.
- Suggestion: define stale-price behavior.
- Specific edit:
  - `spec.md` FR-004 append: "If price snapshot age exceeds freshness limit (e.g., 60s) treat conversion as unavailable and fall through."
  - `plan.md` helper section: include timestamp/freshness check input.

### 4e. Testing Strategy

**E5 — 💡 Recommendation — 100% coverage scope needs explicit boundary**
- Finding: target says 100% for new/modified provider files, while wallet path is high-risk and untested.
- Risk: false confidence if boundary unclear.
- Suggestion: define exactly which files require 100% and add mandatory manual matrix for wallet behavior.
- Specific edit:
  - `plan.md` testing table: list exact coverage target files (`autosign_provider.dart`, config autosign serialization helpers).
  - `plan.md` add manual cases: unknown origin, auth cancel, stale/missing price, >100 component, multi-component mixed.

### 4f. Operational Readiness

**E6 — 💡 Recommendation — Add rollout guard**
- Finding: no feature flag / kill-switch described.
- Risk: fast rollback harder if misclassification appears in production.
- Suggestion: add provider-backed remote/local kill switch default on.
- Specific edit:
  - `plan.md` operational note: "Introduce temporary kill-switch read in wallet autosign branch; if off, force normal notification path."

### 4g. Dependencies & Integration Risks

**E7 — 💡 Recommendation — `SwaptionDomainItem` location causes cross-platform coupling**
- Finding: shared component lives in desktop file but used by mobile.
- Risk: accidental desktop-specific imports/styles leaking into mobile flow.
- Suggestion: move shared widget to platform-neutral path.
- Specific edit:
  - `plan.md` source tree: move `SwaptionDomainItem` to `lib/screens/home/widgets/` or `lib/widgets/swaption/`.
